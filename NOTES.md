- Large local audio files can make the UI look frozen if submitted with `fetch`: the browser does not expose upload progress events there, so the status remains static until the whole request and transcription finish. The file-processing path uses `XMLHttpRequest.upload.onprogress` to keep the UI responsive during multipart transfer, then switches to the generic local transcription status after transfer completes.
- Upload limits have two layers: the route enforces `transcription.max_upload_size_mb` against the actual audio file bytes, while middleware is only a coarse request-body guard. Multipart requests include form-data overhead, so middleware must allow a small multipart-only overhead buffer or it will reject valid files below the configured audio limit.
- VibeVoice ASR source needed by this app is vendored in `vibevoice/` from Microsoft VibeVoice under the MIT license. The app should not rely on a second VibeVoice repository checkout; it loads `app.services.vibevoice_inference` and the local `vibevoice` package. The model itself is `microsoft/VibeVoice-ASR` and will be downloaded by Hugging Face tooling on first real use.
- VibeVoice ASR memory is dominated not only by 7B model weights but also by dtype and generation KV cache. Avoid restoring the demo's `32768` default `max_new_tokens` for normal web requests; it can push a single process into tens of GB. The app defaults to `4096` and MPS auto dtype uses `float16` to avoid fp32 Apple Silicon loads unless explicitly configured.
- VibeVoice ASR uses one cached backend instance per configured model id. Concurrent inference on the same loaded model is rejected with `TranscriptionBusyError`/HTTP 409 instead of queued in-process, which avoids multiple long-running generation calls contending for the same local accelerator memory.
- `mlx-whisper` retains its loaded model in `transcribe.ModelHolder`, and MLX may retain Metal cache allocations. On Apple unified memory, PyTorch reports those allocations as “other allocations”; the router must release the previous framework before switching between MLX Whisper and VibeVoice, while same-backend requests may retain their model.
- A fresh-process VibeVoice failure on a 40-minute recording confirmed a separate, model-intrinsic MPS limit rather than retained Whisper memory. The loaded checkpoint reports 8.67B parameters (roughly 17–18 GB for fp16 weights alone); during single-pass SDPA inference, the process reached about 23 GB of PyTorch MPS allocations plus 70.6 GB of other/shared allocations and exhausted a 96 GB unified-memory machine. Microsoft's advertised 60-minute context is architecture-level capability, not a guarantee that consumer hardware or MPS can run that duration in one pass.
- In that failure, missing `preprocessor_config.json` with fallback defaults, the Qwen tokenizer-class mismatch, and the `torch_dtype` deprecation were warnings; the fatal error was `MPS backend out of memory` inside attention. Do not recommend `PYTORCH_MPS_HIGH_WATERMARK_RATIO=0.0`: removing the safety limit while the machine is already under severe pressure can destabilize macOS. Reducing `vibevoice_max_new_tokens` alone is also insufficient because the long input sequence is the dominant pressure source.
- The practical local-Mac mitigation for long VibeVoice recordings is sequential 10–15 minute chunks, with timestamp offsets and temporary MPS cleanup between chunks. Speaker identities may not remain consistent across chunk boundaries, so cross-chunk speaker reconciliation is a separate concern. On OOM, unload the cached VibeVoice backend and clear MPS memory so the process recovers. True 40–60 minute single-pass processing is better suited to CUDA with Flash Attention or the official vLLM deployment.
